# SEC download cache and retry policy

The SEC ingestor uses `SecClient` for ticker mapping, company submissions, company facts and filing documents. It retains the existing GET-only SEC host/path allow-list, contact user-agent and redirect rejection. The returned buffer is the original response body: source checksums and saved filing manifests continue to refer to those exact bytes.

Responses are cached under `~/.local/share/quant-swarm/cache/sec`, or `SEC_CACHE_DIR`. Each URL/Accept pair has one JSON record containing base64 response bytes, SHA-256, length, URL, representation, original download time, last successful validation time and available ETag/Last-Modified validators. Files are written to private temporary files and renamed into place. Restarting an ingestor reuses verified cache entries; concurrent identical requests within one client share one download.

Ticker/submissions/company-facts responses expire after five minutes. Filing documents expire after 24 hours. After expiry, the client sends available validators. A 304 preserves the bytes and updates validation time; a successful new response replaces the record. Without validators it downloads again. Cached JSON must parse as an object before use. Empty responses, malformed JSON, mismatched metadata and corrupted response bytes cannot be returned as evidence. Invalid cache records trigger an unconditional download. Filesystem permission/I/O failures remain errors rather than being treated as cache misses.

The cache never returns expired content as an outage fallback. If revalidation fails, the ingestion fails and the operator can rerun it later. Removing the cache forces new downloads without removing recorded research artifacts. Include the separate artifact directory in recovery backups; the disposable response cache is not needed to recover recorded evidence.

Requests in one ingestor are serialized with at least 200 ms between starts. Network/timeouts/body-read failures and HTTP 408, 429, 500, 502, 503 and 504 get at most **three total attempts**, each with a 30-second timeout. Backoff is 500 ms then 1 second. Numeric or HTTP-date Retry-After can extend a retry delay to 30 seconds; a longer requested delay fails the ingest immediately instead of retrying early. Permanent HTTP errors (including 403 and 404), unexpected 304 without a usable cache, invalid successful JSON and disk errors do not retry. Cache/revalidation/retry events are logged without the contact header.

The rate limit applies per client process. Run one SEC ingestor and coordinate any other SEC consumers: the [SEC's maximum request rate](https://www.sec.gov/filergroup/announcements-old/new-rate-control-limits) applies across machines, not independently to each worker. Mutable API responses can change as new filings arrive; see the [SEC API documentation](https://www.sec.gov/search-filings/edgar-application-programming-interfaces). Cache TTLs do not establish fundamental-evidence freshness or replace the run's research policy.

Verification: `node --test src/sec-client.test.ts` uses deterministic response/clock fixtures and a real localhost HTTP server. It checks restarts, exact response bytes, TTLs, validators/304, changed content, corruption, request spacing, transient retries, long Retry-After, permanent errors, malformed bodies and failure without stale fallback. No live SEC or model calls are needed.
